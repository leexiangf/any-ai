# 资讯站开发技术大纲

本文说明一个 AI 资讯网站是怎么搭起来的：文章如何管理、页面如何生成、搜索和 SEO 如何实现，以及为什么这样设计。

技术栈：Next.js App Router + TypeScript + Tailwind CSS + Markdown + 静态导出。

---

## 1. 整体思路

站点是「内容驱动 + 构建期生成 + 静态分发」：

```text
Markdown 文章
  → 构建期读取与校验
  → 生成页面、feed、搜索索引、sitemap
  → 导出静态 HTML
  → CDN / 对象存储托管
```

运行时没有数据库、没有常驻后端，访问直接命中静态文件，适合资讯类高频更新、读多写少的场景。

---

## 2. 为什么这样设计

很多人第一反应是「为什么不直接上数据库 + 后台管理系统？」下面把每个关键选择的原因和代价说清楚。

### 2.1 为什么用静态导出，而不是服务端渲染

资讯站的内容在生产时就已经确定，读者看到的页面在同一篇文章上是完全一样的。

- 静态导出的结果是纯 HTML，可以直接放 CDN，访问速度只取决于离用户最近的那个节点。
- 不需要服务器、数据库、容器和运维，也不会有并发瓶颈。
- 页面在构建时就生成好了，运行时不查库，故障面很小。

代价是：如果以后要做登录后个性化推荐、实时评论、实时数据，静态站做不了，需要另外加服务端应用。对资讯站来说，这类需求通常不是第一优先级，先静态起步更划算。

### 2.2 为什么用 Markdown，而不是数据库或 CMS

- 文章就是文件，可以直接用 Git 管理，改动有 diff、有历史、可回滚。
- 迁移成本低：换框架、换托管、换仓库，内容都还在。
- 构建期可以用 Zod 校验字段，缺标题、缺分类、slug 重复会直接构建失败。
- 不需要维护数据库和后台账号体系。

代价是：非技术编辑需要学一点 Markdown 和 Frontmatter。如果团队里编辑很多，可以再加一个轻量后台，但不必一开始就上。

### 2.3 为什么用配置驱动频道结构

频道和二级分类写在 `src/config/taxonomy.json`，页面、导航、sitemap 都从这里读。

- 调整频道名称或顺序不需要改页面代码。
- 分类结构只有一份来源，不会出现导航和页面各写一套的情况。
- 新增一个分类，只要在配置里加一项，再把文章放进对应目录。

代价是：分类结构相对稳定，大量重命名仍然要迁移内容目录。

### 2.4 为什么文章 URL 只保留二级分类和 slug

例如 `/{subcategory}/{slug}/`，而不是 `/{channel}/{subcategory}/{slug}/`。

- 链接更短，分享和记忆成本更低。
- 一级频道以后换名字或调整归属，文章链接不受影响。
- 对 SEO 来说，短而稳定的路径更容易积累权重。

代价是：所有二级分类 id 必须全局唯一，不能两个频道下都有 `release`。

### 2.5 为什么在构建期生成 feed 和搜索索引

- 页面不用每次自己扫一遍 Markdown，读取的是构建期整理好的数据。
- 列表、首页、关于页拿到的是同一份数据，排序和字段不会各写一套。
- 搜索不需要后端服务：浏览器读取一个 JSON，在本地做加权匹配。

代价是：新增文章后必须重新构建。开发阶段用 `npm run dev` 会先重建数据，部署时 `npm run build` 也会自动生成，正常流程不需要手动处理。

### 2.6 为什么不做分页

- 首页和频道页只展示最新的一批内容，避免生成大量低价值页面。
- 站点规模还小时，分页对读者帮助有限，反而增加路由和状态复杂度。
- 需要扩展时再加，不影响现有结构。

代价是：内容量很大以后，需要补充归档页或分页，否则旧文章只能靠搜索和 sitemap 找到。

### 2.7 为什么只有一个浅色主题

- 少一套配色和一套样式覆盖，维护成本直接减半。
- 资讯站以阅读为主，浅色阅读体验稳定。

代价是：不满足喜欢夜间模式的读者。如果以后要做，建议在组件层用 CSS 变量统一实现，而不是到处写 `dark:` 覆盖。

### 2.8 选型总结

| 需求 | 选择 | 原因 |
| --- | --- | --- |
| 页面稳定、访问快 | 静态导出 | 无运行时依赖，CDN 直接分发 |
| 内容可迁移 | Markdown + Git | 不绑定数据库和平台 |
| 结构可调整 | taxonomy 配置 | 改配置不改页面 |
| 链接稳定 | 二级分类 + slug | 频道改名不影响文章 |
| 搜索不额外花钱 | 构建期索引 | 客户端本地匹配 |
| 降低维护成本 | 无分页、单主题 | 少一套逻辑和样式 |

## 3. 项目结构

```text
src/app/                          路由与页面
  page.tsx                        首页
  [topic]/page.tsx                一级频道
  [topic]/[subcategory]/page.tsx  二级分类 + 文章详情
  columns/                        专栏列表 / 专栏详情 / 专栏文章
  tools/                          工具列表 / 工具详情
  topics/ about/ open-source/ update-log/
  privacy/ terms/ contribute/
  sitemap.xml/ sitemaps/ robots.ts

src/components/                   站点壳、导航、搜索、文章、工具组件
src/config/                       taxonomy、导航、专栏、工具、页面配置
src/lib/                          内容读取、分类、专栏、SEO、sitemap
content/posts/                    Markdown 文章
content/columns/                  专栏文章
tools/content/                    feed 与搜索索引生成脚本
public/data/                      构建期生成的数据
```

关键原则：内容放 `content/`，配置放 `src/config/`，读取与转换逻辑放 `src/lib/`，页面只负责组合。

## 4. 文章怎么弄

### 4.1 存放位置

普通文章按「频道 / 二级分类」分目录：

```text
content/posts/{channel}/{subcategory}/{slug}.md
```

例如：

```text
content/posts/agent/mcp/mcp-server-checklist.md
content/posts/llm/release/gpt6-release.md
content/posts/ai-office/doc/workbuddy-team-tutorial.md
```

专栏文章按专栏 id 存放：

```text
content/columns/{columnId}/{slug}.md
```

### 4.2 Frontmatter 字段

```md
---
title: "给智能体接入 MCP：工具注册、权限和调试的三个坑"
slug: "mcp-server-checklist"
description: "文章摘要，用于列表、SEO 和搜索索引。"
date: "2026-11-04"
updated: "2026-11-04"
category: "agent"
subcategory: "mcp"
tags: ["MCP", "Agent", "调试"]
faqs:
  - question: "常见问题"
    answer: "回答内容"
draft: false
---

正文内容...
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 文章标题 |
| `slug` | 是 | 小写英文、数字和连字符，全站唯一 |
| `description` | 是 | 摘要，用于列表、SEO、搜索 |
| `date` | 是 | 发布日期，列表按此排序 |
| `updated` | 否 | 更新时间 |
| `category` | 是 | 一级频道 id |
| `subcategory` | 是 | 二级分类 id，决定文章路径 |
| `tags` | 否 | 标签数组 |
| `faqs` | 否 | 问答数组，同时输出页面区块和 JSON-LD |
| `draft` | 否 | 草稿不参与构建 |

### 4.3 发布一篇文章的流程

1. 在对应频道与二级分类目录新建 `.md` 文件。
2. 填写 Frontmatter，`slug` 不能与已有文章重复。
3. 写正文，支持 Markdown、代码块、表格、Mermaid。
4. `npm run dev` 本地预览，构建会自动校验字段与正文。
5. 提交并构建发布。

没有后台编辑器，写作就是编辑 Markdown 文件，优点是迁移简单、diff 可读、构建期就能发现错误。

## 5. 页面生成原理

### 5.1 内容读取

`src/lib/content.ts` 负责把 Markdown 变成页面能用的数据：

```text
读取 content/posts/**/*.md
  → gray-matter 解析 Frontmatter
  → 日期标准化
  → Zod 校验字段
  → Markdown 转 HTML（代码高亮、标题锚点、目录）
  → 生成 href、摘要、阅读信息
  → 按日期倒序返回文章数组
```

构建期只要 Frontmatter 有问题就直接失败，避免坏页面上线。

### 5.2 分类路由

一级频道和二级分类都由 `src/config/taxonomy.json` 驱动，它是频道结构的唯一来源：

```text
topics[]
  id / label / description
  subcategories[]
    id / label
```

路由只有两个文件：

- `src/app/[topic]/page.tsx`：渲染一级频道。
- `src/app/[topic]/[subcategory]/page.tsx`：同时承担两种页面。

第二个路由的分发逻辑：

```text
第一段是频道 id？
  是 → 渲染二级分类列表页
  否 → 当作文章，第一段是二级分类，第二段是 slug
```

因此文章 URL 是 `/{二级分类}/{slug}/`，不带频道名。这样要求所有二级分类 id 全局唯一。

### 5.3 静态页面枚举

`generateStaticParams` 在构建期告诉 Next.js 要生成哪些路径：

- 分类路由：输出所有「频道 + 二级分类」组合，以及所有「二级分类 + slug」组合。
- 专栏路由：输出所有专栏 id，以及「专栏 id + slug」组合。
- 工具路由：从工具配置输出所有 slug。

配合 `dynamicParams = false`，未枚举的路径直接 404，不会在运行时尝试渲染。

### 5.4 页面组成

- 首页：头条、重点、频道最新文章、最新更新。
- 频道页：频道介绍、二级分类入口、文章列表。
- 文章页：面包屑、标题、正文、FAQ、相关频道、分享。
- 专栏页：章节目录、阅读路径、专栏文章。
- 工具页：浏览器本地运行的工具组件。

页面只做数据组合与展示，业务逻辑留在 `src/lib`。

## 6. 构建期数据

### 6.1 文章 feed

`tools/content/generate-article-feeds.mjs` 读取所有文章，生成：

```text
public/data/feed/all.json
```

首页、频道页、分类页、关于页通过 `src/lib/article-feed-server.ts` 读取这个文件。它相当于构建期的轻量数据层，避免每个页面重复扫 Markdown。

### 6.2 搜索索引

`tools/content/generate-search-index.mjs` 生成：

```text
public/data/search-index.json
```

字段包含标题、摘要、正文纯文本、标签、栏目、日期和链接。

搜索框是客户端组件：打开后 `fetch` 这个 JSON，在浏览器里按标题、描述、正文、标签做加权匹配，并高亮命中词。不需要后端搜索服务。

### 6.3 执行时机

`package.json` 中：

```json
{
  "scripts": {
    "dev": "node tools/content/generate-article-feeds.mjs && node tools/content/generate-search-index.mjs && next dev",
    "build": "node tools/content/generate-article-feeds.mjs && node tools/content/generate-search-index.mjs && next build"
  }
}
```

开发和构建前都会先重建数据，保证页面与文章一致。

## 7. SEO 与站点地图

### 7.1 页面元信息

统一由 `src/lib/seo.ts` 的 `createMetadata` 生成：

- 标题与描述
- canonical
- Open Graph
- Twitter Card
- 文章发布时间与更新时间

文章页额外输出 JSON-LD：

- `BlogPosting`：文章结构化数据
- `BreadcrumbList`：面包屑
- `FAQPage`：有 FAQ 时输出

### 7.2 Sitemap

`src/lib/sitemap.ts` 负责生成：

```text
/sitemap.xml                索引
/sitemaps/core.xml          首页、频道入口、基础页面
/sitemaps/categories.xml    所有频道与二级分类
/sitemaps/columns.xml       专栏与专栏文章
/sitemaps/articles.xml      普通文章
/sitemaps/tools.xml         工具页面
```

每个分片都引用 `/sitemap.xsl`，浏览器查看时可以直接阅读。

### 7.3 Robots

`src/app/robots.ts` 指向 sitemap，静态导出后生成 `robots.txt`。

## 8. 样式与布局

- Tailwind CSS v4，设计变量统一放在 `src/app/globals.css`。
- 站点壳由 `SiteShell` 组合：顶部信息条、主导航、频道条、内容区、页脚。
- 首页与频道页使用固定右侧栏宽度，保证多块内容纵向对齐。
- 只有浅色主题，不做日夜切换，减少维护成本。

## 9. 本地开发与部署

```bash
npm install
npm run dev       # 热开发，默认 3618 端口
npm run build     # 静态导出到 out/
```

项目内还提供三个脚本：

| 脚本 | 作用 |
| --- | --- |
| `shell/restart-dev.sh` | 生成数据、监听文章变化、启动开发服务 |
| `shell/restart-preview.sh` | 构建后用静态服务器预览 `out/` |
| `shell/deploy-cf-pages.sh` | 构建并发布到 Cloudflare Pages |

部署到 Cloudflare Pages：

```text
Build command: npm run build
Output directory: out
```

也可以把 `out/` 上传到任意 CDN 或对象存储。

## 10. 搭建自己的站点

推荐顺序：

1. 用 Next.js App Router 初始化项目，开启 `output: "export"` 与 `trailingSlash: true`。
2. 设计 `taxonomy.json`：先确定一级频道，再给每个频道配二级分类，保证二级分类 id 全局唯一。
3. 建立 `content/posts/{channel}/{subcategory}/` 与 `content/columns/{columnId}/`。
4. 写内容读取层：Markdown 解析、Frontmatter 校验、日期标准化、HTML 转换。
5. 写两个动态路由：一级频道、二级分类与文章共用路由。
6. 用 `generateStaticParams` 枚举所有分类与文章路径。
7. 加首页、专栏、工具、关于等静态页面。
8. 加构建期 feed 与搜索索引脚本。
9. 补 SEO：metadata、JSON-LD、sitemap 分片、robots。
10. 构建、预览、部署。

## 11. 常见坑与规避

### 11.1 内容与路由

- **二级分类 id 重复**：文章路径只保留二级分类，两个频道都用 `release` 会直接冲突，文章链接也会指向错误页面。  
  规避：在 `taxonomy.json` 里保证所有二级分类 id 全局唯一，新增前先全局搜索。
- **文章缺少 `subcategory`**：路径无法生成，构建会失败。  
  规避：Frontmatter 必填，构建期用 Zod 校验，不要靠页面兜底。
- **缺少 `date`**：目录不再按日期组织，无法从路径推断日期。  
  规避：`date` 设为必填，构建期校验。
- **slug 重复**：两篇文章会争用同一个 URL。  
  规避：读取阶段检测重复 slug 并直接报错。
- **把文章放进错误目录**：目录不参与路径计算，但会让人误以为分类由目录决定。  
  规避：目录与 `category` / `subcategory` 必须保持一致，代码评审时检查。

### 11.2 静态导出

- **运行时调用接口或读数据库**：静态导出后没有服务端，构建时能过、上线会坏。  
  规避：所有数据在构建期准备好，页面只读本地数据。
- **未枚举的动态路径**：没有 `generateStaticParams` 的路径会在运行时 404 或无法导出。  
  规避：分类、文章、专栏、工具都要枚举，并设置 `dynamicParams = false`。
- **删改路由后类型报错**：`.next/types` 里残留旧路由的引用。  
  规避：删除 `.next/types` 和 `.next/dev/types` 后重新构建。

### 11.3 数据与搜索

- **新增文章后搜索不到**：搜索读取的是构建期索引。  
  规避：用 `npm run dev` / `npm run build`，它们会先重建索引。
- **feed 与页面不一致**：只改了 Markdown，没有重建数据。  
  规避：不要把 feed 当作手工文件维护，始终由脚本生成。
- **频道没有文章**：频道页会空。  
  规避：发布前检查每个频道和分类的文章数量，必要时先补内容再上线。

### 11.4 展示与 SEO

- **日期格式混乱**：YAML 可能把日期解析成 Date 对象。  
  规避：读取时统一转成 `YYYY-MM-DD` 字符串。
- **重复的 canonical**：同一内容多个路径会分散权重。  
  规避：文章只有一个正式路径，不做多路径兼容。
- **sitemap 里出现草稿或无效路径**：  
  规避：过滤 `draft`，只输出真实存在的页面。
- **首页展示过多**：首屏信息密度过高，加载和阅读都受影响。  
  规避：首页只放头条和有限条目，完整列表交给频道页。

### 11.5 维护成本

- **到处写主题覆盖**：一套浅色主题加一套暗色覆盖，样式会迅速失控。  
  规避：要么只做一套主题，要么统一用 CSS 变量，不要在组件里写两套样式。
- **为不存在的需求提前抽象**：插件系统、通用组件库、复杂状态管理，都会拖慢迭代。  
  规避：先让页面可用，再按真实需求抽象。
- **配置和页面各写一份分类**：导航、sitemap、页面各维护一套频道列表。  
  规避：分类只认 `taxonomy.json`，其他位置都从这里派生。

## 12. 这套方案适合什么场景

适合：

- 资讯站、资讯门户、技术内容站
- 以文章为主、更新频繁、读多写少
- 想低成本部署到 CDN、不想维护数据库
- 希望内容可迁移、可用 Git 管理

不太适合：

- 需要用户登录、评论、投稿后台
- 需要实时数据或复杂交互
- 强依赖数据库查询的后台系统

这类需求可以在现有静态站旁单独加一个服务端应用，而不是把整站改成动态渲染。
