# 插件首篇介绍提示词

> 职责：为**某个具体插件**写它的**首篇介绍文章**——这是该插件目录下 `articles/` 的第一篇，回答「这个插件是什么、解决什么问题、怎么装、怎么用」。存放于该插件目录下的 `articles/` 子目录，围绕它的 GitHub 仓库名、仓库简介、README 与 `plugin-meta.json` 描述，写一篇可被搜索到的「介绍 / 使用文章」。
> 与「插件详情页 SEO」分离：详情页 `seo` 在 `plugin-meta.json`，本提示词只管 `articles/` 下的 `*.md`。
> 与「插件文章页 SEO」的关系：本提示词是其**「首篇介绍」特化版**——只写每篇插件的第一篇介绍，slug、H2 骨架、category 有固定约定；后续的更新动态、进阶教程、使用指南继续用 `docs/提示词/插件文章页SEO提示词.md`。
> 与「通用教程文章」分离：DSH 生态级教程走 `docs/提示词/教程文章写作SEO提示词.md`，不在这里。

## 使用条件

仅在以下情况使用：

1. 为某个插件写它的**首篇介绍文章**（用户指定 GitHub 仓库，如 `liustack/modlens`，且该插件 `articles/` 下还没有介绍文）。
2. 用户明确要求重写某篇插件的首篇介绍。

日常更新插件元数据使用 `docs/提示词/插件接入提示词.md`；后续非首篇的文章用 `docs/提示词/插件文章页SEO提示词.md`；两者都不得使用本提示词。

## 目录与文件结构

文章统一放在插件目录下的 `articles/` 子目录，与 `plugin-meta.json` / `faqs.json` / `plugin-detail.*.md` 分离：

```
src/data/plugins/{category}/{ownerSlug}/{slug}/articles/
├── introduction.zh.md
└── introduction.en.md
```

- `{category}` / `{ownerSlug}` / `{slug}` 与插件 `plugin-meta.json` 一致（`ownerSlug` = GitHub 用户名全小写，`slug` = GitHub 仓库名，小写连字符）。
- 首篇介绍的 `{article-slug}` 统一为 `introduction`（中英两文件同名不同 `locale`）。若该 slug 已存在，改用 `getting-started`；仍冲突则用 `{slug}-introduction`。
- 渲染在 `/plugins/{owner}/{slug}/introduction`，列表页 `/plugins/{owner}/{slug}/articles`。

## 输入

- GitHub 仓库：`[owner/repo]`（如 `liustack/modlens`）
- 插件数据文件：`[src/data/plugins/{category}/{ownerSlug}/{slug}/plugin-meta.json 的绝对路径]`
- 该插件 `plugin-detail.*.md` / `faqs.json`（复用已有事实，勿与之矛盾）

## 核心：围绕「仓库名 / 仓库简介 / 描述」写

一篇文章的信息源优先级（由高到低）：

1. **仓库名（GitHub repo name = 插件 slug）** → 决定文章 slug、标题与正文里的插件名。长尾关键词载体就是它本身（如 `modlens`）。
2. **仓库简介（repo description）** → 一句话定位，作为 `description` 首句与正文「是什么」段的答案。
3. **README / 描述 / `plugin-detail`** → 安装命令、用法、配置、局限，拆分进正文各段。

不要凭空编造功能；一切事实（安装命令、兼容范围、作者、协议、文档路径）都必须来自仓库 README / `plugin-meta.json` / `plugin-detail`，并在关键声明处标注来源。

> **核心关键词** = 仓库名（插件名）+ 本站品牌 `DSH Plugin`（+ `DeepSeek Harness`）。写插件文章 = 蹭仓库热度 + 反哺本站品牌。`DSH Plugin` 不必进标题——落在 `description` / H2 / FAQ / 正文任一即可，但**全文至少命中一处**；标题必须含插件名。

## 允许修改

- 新建 / 改写 `articles/introduction.{locale}.md` 的 frontmatter 与正文。
- 中英文必须成对、结构一致、事实一致。

## 禁止修改

- 该插件的 `plugin-meta.json`、`faqs.json`、`plugin-detail.*.md`（这些走各自的提示词）。
- `src/data/plugin-articles/`（列表页 SEO）、`src/i18n/dictionaries.ts`、`src/lib/*`、`src/plugins-fs.ts`。
- 禁止给文章加 `seo` 字段（文章用 frontmatter 的 `title` / `description`，schema 不支持额外 `seo`）。

## Frontmatter 规则

```yaml
---
title: "…"                  # 中文 ≤60 字符 / 英文 ≤60 字符（见下）
slug: "introduction"        # 首篇介绍固定 introduction，与文件名一致
locale: "zh"                # zh / en
category: "guide"           # 首篇介绍固定 guide
description: "140-155 字（≤160）"  # 首句给答案，含插件名 + 核心长尾词
publishedAt: "2026-08-18"
updatedAt: "2026-08-18"
tags: ["modlens", "视觉", "使用指南"]
draft: false                # true = 不展示、不导出
sources:                    # ≥1 条，GitHub 仓库为主
  - title: "…"
    url: "…"
    publisher: "…"
    accessedAt: "2026-08-18"
faqs:                       # 强制 6 条，q/a 成对
  - q: "…"
    a: "…"
glossary:                   # 相关术语：3-5 条插件关键术语，争夺「术语解释权」
  - term: "ModLens"          # 术语名（含英文原词 / 别名）
    definition: "…"          # 首句 = 一句可独立引用的权威定义
    source: "ModLens README" # 权威来源署名
---
```

- `title`：见「标题规则」。
- `slug`：首篇介绍固定 `introduction`（与文件名一致；冲突时按「目录与文件结构」约定改）。
- `category`：首篇介绍固定 `guide`（使用指南）。
- `description`：**≤160 字符**（中文目标 140-155 字、英文目标 140-158 字符），**写完必须数一遍长度**，超 160 删连接废话、保留核心长尾词；首句直接给答案，自然命中插件名、`DSH Plugin` / `DeepSeek Harness` 与文章核心长尾词。
- **三者对应**：`title`（核心长尾词 + 意图）→ `description`（同一主题上展开「是什么 + 为什么值得看」）→ 正文核心（兑现标题承诺）。description 禁止写与文章核心无关的泛词、禁止堆砌与正文无关的关键词。
- `tags`：≥3 个，中文版中文标签、英文版英文标签。
- `sources`：至少 1 条，主来源为 GitHub 仓库；**`url` 只允许 `https://github.com/` 开头的链接**，含 `accessedAt`。
- `faqs`：**强制 6 条**（一条不能少、不能多，参考 `scripts/bin/prompts/04-faqs.md`），中英成对。从 README / 参考信息主动挖掘该插件「真实会遇到」的具体问题，**禁止套「是什么 / 怎么安装 / 怎么重启」通用模板**。挖掘方向：某个配置项或命令怎么用、默认值；使用限制 / 坑 / 边界；怎么触发某能力、怎么排查常见报错；依赖 / 权限 / 前置条件。**q 必须是完整问句**（zh 20~50 字），写成用户会搜索的样子、具体到这个插件（换插件名就说不通），至少 1~2 条 q 带「DSH plugin」/「DeepSeek Harness」。**a 与 q 严格对应**（zh 60~100 字、2~4 句），事实与正文 / `plugin-detail` 一致，只写 README / 参考信息里有的内容，禁止编造。**回答首句先给独立结论**：一句可脱离上下文独立成立、自然带核心词的完整答案（FAQ 的 q/a 本身是长尾词落点、也是 AI 摘要引用的来源）。**可以出现命令**（安装 / 配置 / 使用命令），但**严禁编造包名**；**禁止出现任何超链接**（含 GitHub 链接、本站内链）。不写 star 数、日期、版本号。
- `glossary`：3-5 条该插件的关键术语 + 权威解释，是**「术语解释权」流量的载体**——AI 回答「XX 是什么意思」时优先引用这里的定义。选词：插件名本身 / README 里的核心概念与专有名词 / 用户常搜的别名；`definition` **首句 = 一句能脱离上下文单独成立、可被 AI 直接引用的权威定义（「X 是 Y」式）**，第二句起再补细节；`source` 标注权威来源（GitHub README）。渲染为页面可见「相关术语」区块 + `DefinedTermSet` JSON-LD，定义必须与正文一致、禁止编造。

## 标题规则

- 结构：`{插件名} 是什么 / 怎么用？{补充}`，突出「是什么 / 解决什么问题」——这是首篇介绍的主搜索意图。
- **标题 = 文章核心的浓缩**：必须含插件名 + 文章主长尾词 + 意图词，与正文核心一一对应；用户拿标题搜索、点进文章，正文必须给出标题的答案。
- 中文 ≤60 字符、英文 ≤60 字符。
- 禁止具体 star 数、版本号。

示例：
- zh：`ModLens 是什么？让 DeepSeek Harness 纯文本模型看懂图片`
- en：`What Is ModLens? Give DeepSeek Harness Text-Only Models Sight`

## 正文规则

- 首个 H1 由 frontmatter `title` 生成，正文从 `##` 开始，不要重复 H1。
- **Answer-First**：每个 `##` 段首句用加粗给结论，再展开解释。
- 内容深度：中文 ≥500 字、英文 ≥300 词；覆盖「是什么 → 核心功能 → 安装启用 → 典型用法 → 适用场景与注意 → 项目链接」。
- 关键事实（安装命令、兼容、作者、协议、文档路径）标注来源，链接到 GitHub 仓库。
- 站内内链：插件详情页 `/plugins/{owner}/{slug}` 在「这是什么」段**首次提到插件名时内链一次**（首次出现原则）；「项目链接」段再集中放 GitHub 外链 + 插件详情页 + 插件市场 `/plugins` 内链。
- 中英两版事实一致，不要求逐字翻译；不堆砌关键词、不写套话。

### 首篇介绍 H2 骨架（固定，按顺序写）

正文是 Markdown，六个 `##` 是 H2 标题标签，**必须原样输出**（`## ` 开头），缺一不可、不得删改、不得调序、不得合并。六段 H2 骨架与顺序固定（措辞按下面弹性处理）：

```
## {插件名} 是什么？                      # 定位段：首句给「{插件名} 解决 {某问题}」的闭环结论，再 3~5 句展开「是什么 → 解决什么问题 → 核心能力」
## {插件名} 的核心功能有哪些？              # 列表式：按 README 列 3~6 条真实能力，每条独立成立可被 AI 引用
## 怎么安装与启用 {插件名}？       # 安装 + 启用，编号步骤（命令完整可执行）
## {插件名} 典型用法              # 使用示例，编号步骤（命令完整可执行）
## 适用场景与注意                # 适用场景 + 限制 / 兼容 / 注意事项
## 项目链接                      # GitHub 仓库外链 + 插件详情页 /plugins/{owner}/{slug} + 插件市场 /plugins 内链
```

- **段首即结论**：每个 H2 第一句必须是脱离标题也独立成立的结论句（「X 是 Y」「要做 Z 就执行 W」），禁止铺垫、设问开头。
- **H2 骨架固定、表意弱时鼓励带插件名或问句化**：六段顺序与主题固定，措辞不锁死——「这是什么」「核心功能」这类表意弱的通用词，鼓励问句化并自然带插件名（如「{插件名} 是什么？」「{插件名} 的核心功能有哪些？」）；但不要每个 H2 都生硬前缀插件名。`DSH Plugin` / `DeepSeek Harness` 核心词由**正文段首句与内容**自然命中，不堆在 H2 上。
- **「安装与启用」「典型用法」用 1/2/3/4 编号步骤**（过程感），每步 = 一个可执行动作 + 预期结果；安装、配置、使用命令都要写全，禁止连贯散文描述「怎么做」。
- **「项目链接」放 GitHub 外链 + 插件详情页内链 + 插件市场内链**：GitHub 链接只允许 `https://github.com/` 开头，不引第三方站点；同时内链 `/plugins/{owner}/{slug}`（插件详情）与 `/plugins`（插件市场）。

### 命令与链接规则

1. **任何命令都可以写**：安装（`dsh plugin add …`）、更新、卸载、使用、配置命令全部可以写进正文，且必须写完整、可照着执行（写进「安装与启用」「典型用法」的编号步骤里）。
2. **外链只允许 GitHub 链接**：只允许 `https://github.com/` 开头的链接（仓库主页、README、Issues），禁止任何非 GitHub 链接。
3. **必须保证权威**：命令与事实一律来自 GitHub README / `plugin-meta.json` / `plugin-detail` 原文，不编造；外链只引 `https://github.com/` 官方一手来源，关键声明后标注 `（[来源](URL)）`。

## AI 可引用结构（被 AI 摘要引用）

- **每个 H2 段首给一句独立成立的定义/结论句**：「X 是 Y」或「要做 Z 就执行 W」，一句话说清，首句即结论，末尾注明来源 `（[来源](URL)）`。禁止需要上下文才懂的半句。
- **每条 FAQ 回答首句先给独立结论**：第一句为完整可被引用的答案（定义式/结论式），第二句起再补命令、步骤、版本；可写命令、禁止任何超链接。FAQ 内容是长尾词落点、也是 AI 摘要引用的来源，首句必须能脱离上下文单独成立。
- **H2 标题用固定骨架、表意弱时问句化**：六段顺序固定（`{插件名} 是什么？` / `{插件名} 的核心功能有哪些？` / `怎么安装与启用 {插件名}？` / `{插件名} 典型用法` / `适用场景与注意` / `项目链接`），禁用「安装方式」「更多信息」「前言」这类无指向标题。
- **「是什么 / 核心功能 / 怎么用」只讲本插件方案**：围绕仓库名写，不对照罗列竞品，蹭仓库热度反哺本站品牌。
- **每条 `glossary` 术语的 definition 首句给权威定义**：以「X 是 Y」式独立成句（AI 回答「XX 是什么意思」时直接抽走），末尾（或 `source` 字段）标注权威来源。

## 验收

- 只新建/改写 `articles/introduction.{locale}.md`，未动 `plugin-meta.json` / `plugin-detail` / 列表页配置。
- 中英成对、`slug: introduction`、`category: guide`、`draft: false`。
- 标题必含插件名；全文至少命中 1 次 `DSH Plugin`（标题 / H2 / FAQ / 正文 / `description` 均可）。
- 标题 ≤60 字符且含核心长尾词；description ≤160 字符（写完数一遍）且首句给答案；标题 / description / 正文核心三者对应。
- H2 六段骨架齐全（{插件名} 是什么？ / {插件名} 的核心功能有哪些？ / 怎么安装与启用 {插件名}？ / {插件名} 典型用法 / 适用场景与注意 / 项目链接）、骨架固定表意弱时已问句化带插件名；「安装与启用」「典型用法」为编号步骤，安装/使用命令完整可执行；命令与事实来自官方一手来源、外链只引 `https://github.com/` 开头的链接。
- `faqs` 强制 6 条，q 为完整问句（zh 20~50 字）且具体到插件、至少 1~2 条带 `DSH plugin` / `DeepSeek Harness`；a 与 q 对应、可写命令、禁止任何超链接、无编造包名。
- `glossary` 3-5 条、术语定义首句可独立引用、`source` 标注权威来源、与正文一致不编造。
- 事实来自 GitHub 仓库 / `plugin-meta.json` / `plugin-detail`，关键处标注来源。
- `npx tsc --noEmit` 通过、`git diff --check` 通过、文章能出现在 `/plugins/{owner}/{slug}/articles` 列表。
- 不要提交代码。
